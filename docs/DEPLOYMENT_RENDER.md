# Deployment Guide — Render (single web service)

This deployment serves the built React app and Express API from the **same origin**. That preserves the existing frontend's relative `/api` requests and avoids cross-origin cookie setup. The patch adds production static-file serving to Express and a database-aware `/api/health` endpoint.

## Before publishing

1. Run the local verification in `docs/RELEASE_TEST_PLAN.md`.
2. Rotate the Gemini key if it was ever exposed. Keep the new key only in server-side secrets.
3. Make sure `.gitignore` excludes `.env`, `server/.env`, uploads, logs, backups and generated build directories.
4. Use a private GitHub repository while preparing the release. Do not commit `.env` or a database dump.
5. Push the project root (the folder containing `client/` and `server/`) to GitHub.

## Create the database first

Create a managed PostgreSQL database and copy its connection URL. Use a provider and plan whose persistence, backups, limits, and pricing meet your needs. If the provider requires TLS, set `DATABASE_SSL=true` in the web service; use the provider's documented connection string. Never commit the connection URL.

**Render free Postgres caveat:** Render's free Postgres databases expire 30 days after creation and have no backups. Do not use one for important or long-lived demo data. A free Render web service can still connect to a separately hosted PostgreSQL database. Review the provider's current terms before selecting it.

## Deploy with the included Blueprint

1. Sign in to Render and choose **New → Blueprint**.
2. Connect the GitHub repository containing this project and select the branch to deploy.
3. Render reads `render.yaml`. The web service is configured for Node.js 22, `npm ci` installs, both production builds, migration on start, and `/api/health` health checks.
4. In the service's Environment settings, set the prompted secret values:
   - `DATABASE_URL`: managed PostgreSQL connection string.
   - `DATABASE_SSL`: `true` if the provider requires TLS; otherwise set `false` only when the provider says SSL is not required.
   - `GEMINI_API_KEY`: your current Gemini API key.
   - `JWT_SECRET`: generated by Render from the Blueprint. Keep it private.
5. Deploy and watch the build logs. The start command applies the idempotent schema migration and then starts the server. It does **not** run the demo seeder.
6. Open the deployed `https://...onrender.com` URL. Verify `/api/health` returns HTTP 200 with `ok: true` and `database: "connected"`.

## Create the first production administrator

Do not seed the demo accounts on production. First register your own account through the application. Then use your database provider's SQL editor to promote it. Replace the email below with the email used during registration:

```sql
UPDATE users
SET role = 'admin', department = NULL
WHERE lower(email) = lower('your-real-email@example.com');
```

Sign out and sign in again so the updated role is reflected in the session. Keep the admin email private and use a strong password. To create officers, register those accounts and update their roles/department through the database administrator's SQL editor, for example:

```sql
UPDATE users
SET role = 'officer', department = 'Water Department'
WHERE lower(email) = lower('officer-email@example.com');
```

Never accept role or department changes from an ordinary public profile form.

## Known deployment limitations

- Free Render web services spin down after inactivity, so the first request may be slow.
- This app currently stores uploaded photos on the local filesystem. Free hosting filesystems can be ephemeral, so photos may be lost on restart/redeploy. For durable photos, integrate object storage (S3-compatible storage, Cloudinary, etc.) or an appropriate persistent disk before treating uploads as production storage.
- In-app notifications poll periodically; this is not WebSocket push. Email delivery requires a configured email provider and is not enabled by this guide.
- `npm run ai:check` consumes Gemini API quota. Do not run it in CI or on every deploy; use it during controlled manual verification.
- The app is an independent prototype, not connected to official municipal/government grievance systems.

## Rollback

Render retains deploy history and can redeploy a previous successful commit. Database schema migrations in this project are additive, but always back up the database before future destructive schema changes. Keep the timestamped local backups created by the patch script until the deployed version is verified.
